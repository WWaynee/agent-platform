# 需求单 0003：文档维度检索 + 文档级控制能力（按文档过滤 / 文档身份透传 / 整文档语境）

- 状态：✅ **已实现并验证**（阶段1 文档维度检索 + 阶段2 文档级工具 + 阶段3 ReAct 编排已落地；e2e 硬性断言 + 单测 + 存量向量重建 + `go vet/test/build` 全通过，详见文末「实现与验证记录」）
- 优先级：🟡 中（补齐 RAG 检索的"文档维度"能力，解决"在所有片段里搜噪声大 / LLM 不知道来源 / 拿不到整文档语境"三大短板；为文档级分析（对比/总结/定位具体文档）铺路）
- 模块：`storage`（Qdrant payload / 检索过滤 / 文档搜索）、`api/service`（检索与文档搜索）、`toolkit`（三个新工具 + 改造知识库工具）、`agent/engine`（System Prompt）、`cmd/api`（工具注册 / 默认工具配置）
- 创建日期：2026-08-17
- 完成日期：2026-08-18

> 设计要点（相比现状的核心变化）：
> ① 检索从"全租户所有片段里搜"升级为**可按 `document_ids` 限定在某几个文档里搜**，且 LLM 知道每个片段来自哪个文档（`document_id` + `document_name` + `chunk_index`）；
> ② 新增**文档列表 / 文档全文 / 文档名搜索**三个工具，让 LLM 先"知道有哪些文档 → 匹配名称得 ID → 限定检索 → 必要时读全文"，从而承载"对比文档 A 与 B""总结文档 A"这类整文档级问题；
> ③ 用 **A+B 结合的"名称→ID 解析"**：文档少直接 list_documents 全量、LLM 自己匹配；文档多时用 search_documents 按关键字先搜再匹配；
> ④ 多租户隔离底线不变：所有新检索/搜索仍强制 `tenant_id` 过滤，新增 `document_ids` 过滤只是**叠加**在租户过滤之上，绝不削弱隔离。

## 一、功能现状与缺失

当前知识库检索是**全租户平铺式**：一次提问会把"当前租户所有文档的所有片段"混在一起检索，返回的每条命中只有 `content / score / document_id / chunk_index`，没有文档名，也没有"只在这几个文档里搜"的能力。由此产生三大缺失：

| 缺失能力 | 导致的问题 | 典型问不出来的问题 |
|----------|-----------|--------------------|
| 按文档过滤 | 每次都在全租户所有片段里搜，噪声大 | "对比文档 A 和文档 B 的差异" |
| 文档身份透传 | LLM 不知道片段来自哪个文档，无法引用来源、无法区分不同文档观点 | "文档 A 里怎么说，文档 B 里怎么说" |
| 整文档语境 | 只有碎片，看不到文档结构和完整上下文 | "总结一下文档 A 的核心观点" |

### 1. 检索链路现状

`toolkit/knowledge_retrieve.go` 的 `KnowledgeRetrieveTool.Execute`：

```go
// 当前只解析 query，没有 document_ids；topK 固定 3
var req struct {
	Query string `json:"query"`
}
hits, err := service.Search(ctx.ToContext(nil), ctx.TenantID, req.Query, 3)
// 拼回给 LLM 时只带 content + DocumentID
fmt.Fprintf(&b, "[%d] 文档ID=%d 相关度=%.3f\n%s\n\n", i+1, h.DocumentID, h.Score, h.Content)
```

### 2. 向量写入现状（payload 已含 document_id / chunk_index / tenant_id，缺 document_name）

`storage/qdrant.go` 的 `toPointStruct` 已把 `tenant_id / document_id / chunk_index / content` 写进 payload，但**没有 `document_name`**——LLM 无法知道片段属于哪篇文档（只能靠数字 ID 反查）。文档名是检索结果展示/引用来源的关键，需补齐。

### 3. 缺失的文档级工具

当前只有 `knowledge_retrieve` 一个工具。LLM 无法"先看有哪些文档"，也无法"读某篇文档全文"，因此对"合同 A 里的付款条款""对比两份合同"这类问题无从下手，只能硬把用户提的自然语言文档名当成 query 全库检索，噪声大且无法区分。

## 二、改进目标

分三阶段落地，目标依次为：

### 阶段 1（必做）：给检索加上"文档维度"
1. 确认/补齐 Qdrant payload：`document_id`（已有）、`document_name`（**新增**）、`chunk_index`（已有）、`tenant_id`（已有）。
2. 改造 `knowledge_retrieve` 工具入参，增加**可选** `document_ids` 过滤参数。
3. Qdrant 查询时在 `tenant_id` 过滤之上叠加 `document_id in [...]` 过滤。
4. 检索结果返回带上 `document_id / document_name / chunk_index`，LLM 知道每个片段来自哪篇文档、可引用来源。
5. 更新工具 `Description`，告诉 LLM 可以传 `document_ids`。

### 阶段 2（推荐）：增加"文档级"控制能力
1. 新增 `list_documents` 工具：返回当前租户所有文档（id/name/size/status/时间），供 LLM 先知道有哪些文档。
2. 新增 `get_document_content` 工具：返回某篇文档的完整文本（**带长度限制**，超过阈值截断或只返回前 N 片段 / 摘要 + 关键片段）。
3. 新增 `search_documents` 工具（按名称 `LIKE` 模糊搜索，文档多时用）。
4. （可选）文档处理完成后预生成摘要存 `documents.summary`，供 list_documents 返回、帮 LLM 选文档。
5. 三个工具注册进 ToolManager，并纳入新租户默认工具配置。

### 阶段 3（配合）：ReAct 侧编排
1. System Prompt 更新：告诉 LLM 新工具能力与"名称→ID 解析"的多文档推理路径。
2. 边界情况处理规则写入 Prompt：匹配不到 / 匹配到多个 / 用户未提具体文档时的正确行为。

## 三、方案设计

### 3.1 阶段 1：文档维度检索

> **关联确认（删除文档时 Qdrant 向量清理——已存在，无需本需求新增）**：审代码确认 `api/service/document.go` 的 `DeleteDocument` 已含第 3.5 步 `storage.DeleteVectorsByDocument(ctx, tenantID, id)`——按 `tenant_id + document_id` 双键过滤删除该文档全部向量。因此删除文档后**不会再残留孤儿向量**，本需求的 `document_ids` 过滤不会命中已删除文档的片段，`document_name` 清理语义与现有删除逻辑一致，无需重复实现。

#### （2）`storage.SearchVectors` 支持可选 `document_ids` 过滤

在现有强制 `tenant_id` 过滤之上，叠加 `document_id in [...]`：

```go
// 在 tenantIDFilter 基础上，若传了 document_ids，再叠加 document_id 的 Match 任意值条件
func SearchVectors(ctx context.Context, query []float32, tenantID uint64, topK int, documentIDs ...uint64) ([]QdrantSearchHit, error) {
	conditions := []*qdrant.Condition{
		{ ConditionOneOf: &qdrant.Condition_Field{ Field: &qdrant.FieldCondition{
			Key: "tenant_id",
			Match: &qdrant.Match{ MatchValue: &qdrant.Match_Integer{ Integer: int64(tenantID) } },
		}}},
	}
	if len(documentIDs) > 0 {
		ids := make([]int64, 0, len(documentIDs))
		for _, id := range documentIDs {
			ids = append(ids, int64(id))
		}
		conditions = append(conditions, &qdrant.Condition{ ConditionOneOf: &qdrant.Condition_Field{ Field: &qdrant.FieldCondition{
			Key: "document_id",
			Match: &qdrant.Match{ MatchValue: &qdrant.Match_Integers{
				Integers: &qdrant.RepeatedIntegers{ Integers: ids },
			}},
		}}}) // document_id in [1,2,3]
	}
	req.Filter = &qdrant.Filter{ Must: conditions }
}
```

- `documentIDs` 用可变参数，**不传即为全租户检索（兼容老逻辑）**。
- 过滤条件用 qdrant-go 的 `Match_Integers`（整型字段的"in 列表"匹配），配合 `qdrant.RepeatedIntegers` 传 `int64` 列表。
- `tenant_id` 过滤仍由本函数内部强制构造（传进来也不信，隔离底线 stays）——`document_ids` 只是在此之上再收敛范围；即使误传别的租户的文档 ID，也会被 `tenant_id` 过滤兜住。

**`document_ids` 入参边界校验（必做，见下方口径统一）：**

| 输入情形 | 处理口径 |
|----------|----------|
| `document_ids` 为空数组 `[]` | **等同不传** → 全租户检索，不报错 |
| `document_ids` 全为无效 ID（0 / 负数 / 不存在的 ID）| **等同不传** → 全租户检索，不报错 |
| 有效 + 无效 ID 混在一起 | **只取有效 ID** 过滤，无效的被 `tenant_id`/存在性过滤隐式忽略 |
| 传了其他租户的文档 ID | 被 `tenant_id` 过滤兜住，返回空（不报错）|

> 统一约定：**`document_ids` 里 `<=0` 的项一律剔除**；剔除后仍非空则以剩余有效 ID 过滤；剔除后为空则退回全租户检索。这样 LLM 误传 `0`/`-1` 不会被误伤成"搜不到任何内容"。

#### （3）`api/service/knowledge.go`：`Search` 增加 `documentIDs`，`SearchHit` 带文档名

```go
type SearchHit struct {
	Content      string  `json:"content"`
	Score        float32 `json:"score"`
	DocumentID   uint64  `json:"document_id"`
	DocumentName string  `json:"document_name"` // 新增：文档名称
	ChunkIndex   int     `json:"chunk_index"`
}

func Search(ctx context.Context, tenantID uint64, query string, topK int, documentIDs ...uint64) ([]SearchHit, error) {
	// 检索时透传 documentIDs
	hits, err := storage.SearchVectors(ctx, resp.Vector, tenantID, topK, documentIDs...)
	// 组装时从 payload 取 document_name
	out = append(out, SearchHit{
		Content: h.Content, Score: h.Score,
		DocumentID:   payloadUint64(h.Payload, "document_id"),
		DocumentName: payloadString(h.Payload, "document_name"), // 新增取文本
		ChunkIndex:   int(payloadUint64(h.Payload, "chunk_index")),
	})
}

// payloadString 从 payload 安全取字符串字段；缺失返回空串。
func payloadString(payload map[string]interface{}, key string) string
```

> **边界收敛统一（重要）**：`top_k` 的 clamp（默认 3、上限 10）与 `document_ids` 的无效值剔除（`<=0` 丢弃、剔除后为空退回全租户），**统一收敛在 `service.Search` 这一个入口**（HTTP handler 与 Agent 工具都调到它，避免两处重复实现口径不一）：

```go
const (
	defaultSearchTopK = 3 // 默认返回条数
	maxSearchTopK     = 10 // 单次上限：防止 LLM 传 100 把大量片段一次性塞回上下文
)

func Search(ctx context.Context, tenantID uint64, query string, topK int, documentIDs ...uint64) ([]SearchHit, error) {
	// ① top_k 收敛：<=0 → 默认3；>10 → 压到10
	if topK <= 0 {
		topK = defaultSearchTopK
	} else if topK > maxSearchTopK {
		topK = maxSearchTopK
	}
	// ② document_ids 净化：剔除 <=0 的项；剔除后为空说明调用方本意是"全租户"，按不传处理
	validIDs := make([]uint64, 0, len(documentIDs))
	for _, id := range documentIDs {
		if id > 0 {
			validIDs = append(validIDs, id)
		}
	}
	// ③ 检索（tenant_id 隔离在 storage 强制；document_ids 仅在其上收敛范围）
	hits, err := storage.SearchVectors(ctx, resp.Vector, tenantID, topK, validIDs...)
	// ...
}
```

### 3.2 阶段 2：文档级控制能力

#### （1）`storage/document.go` 新增按名称搜索 + 供词

```go
// SearchDocuments 按文档名模糊搜索（LIKE 关键字），强制 tenant_id 过滤、排除软删。
// 返回当前租户中名称含 keyword 的文档（按更新时间倒序）。
func SearchDocuments(ctx context.Context, tenantID uint64, keyword string) ([]model.Document, error) {
	query := DB.WithContext(ctx).Where("tenant_id = ?", tenantID)
	if keyword != "" {
		// GORM 参数化 LIKE，天然防注入（特殊字符 % _ 作为字面量处理，本需求接受该行为）
		query = query.Where("name LIKE ?", "%"+keyword+"%")
	}
	return query.Order("updated_at DESC").Find(&list)...
}
```

#### （2）新增 `toolkit/list_documents.go`：`ListDocumentsTool`

- 工具名 `list_documents`，入参无（或可选 `keyword`）。
- 返回当前租户全部文档：`[{id, name, size, status, created_at}]`（`WHERE tenant_id=? AND deleted_at IS NULL`，用 `storage.ListDocuments` 分页拉取或新增不分页全量方法）。
- **返回上限 50 篇**（按更新时间倒序）：文档多（如 200 篇）时避免一次全量返回撑爆 token、LLM 也看不过来。超过 50 篇时在返回末尾追加提示："文档较多（共 N 篇），已返回最近 50 篇；请用 search_documents 按名称精确搜索。"
- `Description`：明确"当用户提到具体文档（如"合同A"）时，先调用此工具获取文档 ID；也用于让 LLM 了解企业有哪些文档、便于决定检索哪几篇。文档较多时返回有上限"，并提示"文档多时优先用 search_documents 按名称搜"。
- 租户隔离：从 `ctx.TenantID` 取租户，`storage.ListDocuments` 已强制过滤。

#### （3）新增 `toolkit/search_documents.go`：`SearchDocumentsTool`

- 工具名 `search_documents`，入参 `keyword` 必填。
- 逻辑：`WHERE tenant_id=? AND name LIKE '%keyword%'` 模糊搜索，返回匹配文档 `[{id, name, size, status}]`。
- `Description`：明确"当知道文档的模糊名称（如'合同'）但文档很多、需要在名称里精确检索时用；文档少也可直接用 list_documents。"
- 空 keyword / 无匹配：返回空数组与提示，不报错。

#### （4）新增 `toolkit/get_document_content.go`：`GetDocumentContentTool`

- 工具名 `get_document_content`，入参 `document_id` 必填。
- 逻辑：带租户过滤取文档 → `storage.DownloadFile(minioKey)` 读全文 → **按字符数上限截断**。
- **长度估算（建议按中文场景为主设定）**：字符数 → token 的换算差异大——
  - 中文：1 字符 ≈ 1～1.5 token；
  - 英文：1 token ≈ 4 字符，4000 字符 ≈ 1000 token。
  为通用安全、**按字符数设上限 `MaxDocumentChars = 8000`**（中文场景约 8K~12K token，仍远小于常见上下文窗口；英文场景更保守）。宁可保守、别超窗口。截断时只返回前段，并在末尾提示"文档过长，已截断到前 N 字符，如需特定部分可用 knowledge_retrieve 精确检索"。

```go
const MaxDocumentChars = 8000 // 字符上限（中文 1字符≈1~1.5 token；保守取 8000，避免超上下文窗口）
func (GetDocumentContentTool) Execute(ctx, params) (string, error) {
	var req struct{ DocumentID uint64 `json:"document_id"` }
	// 1. 带租户过滤读取全文（storage.ReadDocumentContent）
	txt, err := storage.ReadDocumentContent(ctx.ToContext(nil), ctx.TenantID, req.DocumentID)
	// 2. 超限裁前 8000 字符 + 提示；未超限全量返回
	// 3. 返回时注明文档名，便于 LLM 引用来源
```

### 3.3 名称→ID 解析（A+B 结合）

用户说"合同 A 是自然语言名称，`knowledge_retrieve` 要的是数字 ID"，中间需要一步"名称解析"。

**方案 A（文档少 <50 篇）：`list_documents` 全量返回，LLM 自己匹配**
- 用户"合同A里的付款条款是什么？"→ LLM 调 `list_documents` → 拿到 `[{id,name,...}]` → LLM 把"合同A"匹配到 `id` → 调 `knowledge_retrieve(document_ids=[id], query="付款条款")`。

**方案 B（文档多 ≥50 篇）：`search_documents` 按名称模糊搜**
- 用户"合同A里的付款条款？"→ LLM 调 `search_documents(keyword="合同A")` → 拿到匹配 `[{id,name}]` → 匹配到 `id` → 调 `knowledge_retrieve(document_ids=[id])`。

**结合策略**：文档少时 LLM 自然用 list_documents 全量即可；文档多时用 search_documents 先搜再匹配。两者都提供，由 System Prompt 引导 LLM 按文档数量权衡。
