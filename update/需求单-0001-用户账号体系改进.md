## 一、功能现状

当前用户账号体系采用「公开注册 + 自报租户」的模式，主要存在以下问题与现状：

### 1. 注册接口（`POST /api/user/register`）
- 公开路由组，**无需登录**即可调用。
- 请求体为 `tenant_id`（必填）、`username`、`password`、`role`（可选，允许 `admin/member`）。
- `service.Register` 直接接收前端传入的 `tenant_id` 和 `role` 落库。

### 2. 登录接口（`POST /api/user/login`）
- 公开路由组，携带 `tenant_id` + `username` + `password` 登录，成功签发 JWT。
- 登录不校验用户所属租户是否有效/启用。

### 3. 创建租户接口（`POST /api/tenant`）
- **私有路由组**（需登录），但**任何登录用户（含普通 member）都能建租户**，无角色限制。
- 该接口当初是基于「接入 JWT 演示路由分组」挪入私有的，并无严格的业务权限设计。
- 创建租户时自动创建首个 `role=admin` 账号 + 初始化默认工具配置，但**无事务包裹**：任一步失败会留下残缺租户。

### 4. 多租户隔离的可信来源
- 文档 / 检索 / 会话 / 工具配置等接口的 `tenant_id` 一律从 JWT 上下文拿，不信前端。
- 唯独注册 / 登录是公开接口、只能靠前端自报 `tenant_id` —— 是全链路唯一信任前端自报 `tenant_id` 的口子。

## 二、存在的问题

| # | 问题 | 危害 | README 关联 |
|---|------|------|------------|
| A | 注册可传**任意 `tenant_id`**，且**不校验该租户是否存在** | ① 可冒充混入真实存在的公司；② 可凭空编造不存在的租户 ID，造出「无主租户孤儿账号」，绕过正常租户创建流程 | 待补齐项 3 |
| B | 注册可传 `role="admin"` | 匿名用户能在任意租户里自助建**管理员**账号，实现提权 | 待补齐项 2 |
| C | 登录 / 注册不校验用户所属租户有效性与启用状态 | 孤儿账号 / 禁用租户内的账号仍可登录 | 待补齐项 11 |
| D | 创建租户 + 首个 admin + 工具配置**非原子** | 某一步失败会留下「无管理员的残缺租户」 | — |
| E | 创建租户放私有组却是「任何登录用户可建」，权限语义混乱 | 未真正限制"谁能建租户"，且与「公开注册租户」目标冲突 | 待补齐项 1 |

## 三、改进目标

在**取消平台级超管、租户级超管、审批机制**（认定为 demo 非 P0 功能）的前提下，把用户账号体系收敛为简单、安全、符合多租户隔离原则的模型：

| 角色 | 产生方式 | 审核 | 数量 |
|------|---------|------|------|
| 租户（公司） | **公开注册**（注册成功同时原子创建首个 admin） | 无 | 多个 |
| 租户 admin | 建租户时自动生成 / 后续公开注册 | 无 | 多个 |
| 租户 member | 公开注册 | 无 | 多个 |
| 平台级超管 / 审批流 | **取消** | — | — |

核心安全底线：
1. 注册 / 登录**必须校验租户存在**（堵问题 A、C）。
2. 建租户时首个 admin **固定 `role=admin`**，不可提权（堵问题 B）。
3. 建租户 + 首个 admin + 工具配置**原子执行**（堵问题 D）。
4. 公开注册租户，但「查租户列表 / 详情 / 改状态」仍保持受控（避免外部枚举租户）。

## 四、改进方案

### 4.1 接口调整（路由）

```
公开组（无需登录）：
  POST /api/tenant/register   # 新增：注册租户（原子创建租户 + 首个 admin + 工具配置）
  POST /api/user/register     # 保留：注册 admin/member，补租户存在校验
  POST /api/user/login        # 保留：登录，补租户存在/启用校验
  GET  /health

私有组（需登录）：
  GET  /api/tenant/list       # 保留私有，禁止外部枚举所有租户
  GET  /api/tenant/:id        # 保留私有
  POST /api/tenant            # 原有 CreateTenant 保留私有（管理员视角建租户），或与 /tenant/register 归并
  PUT  /api/tenant/:id/status # 保留私有（管理操作）

其余私有接口（文档 / 检索 / 会话 / chat 等）不变。
```

> 说明：`tenant/list`、`tenant/:id`、`tenant/:id/status` **不随注册挪公开**，维持受控，避免公开枚举 / 越权改状态。

### 4.2 数据层改动

**1. 新增「注册租户」原子业务方法（`api/service/tenant.go`）**

新增 `RegisterTenant(ctx, tenantName, adminUsername, adminPassword) (*model.Tenant, *model.User, error)`，内部用 `storage.DB.Transaction` 包裹：

1. `CreateTenant`（建租户，状态默认启用）
2. `Register`（创建首个账号，**固定 `role="admin"`**，禁止调用方传 role）
3. `InitDefaultToolConfigs`（初始化该租户默认工具配置）
4. 任一步失败 → 整体回滚

将现有 `CreateTenant` 内部逻辑重构为共用该事务方法，避免逻辑重复。

**2. 注册 / 登录补租户存在校验（`api/service/user.go`）**

- `Register`：进入后先 `storage.GetTenantByID(tenantID)` 校验租户存在，不存在返回明确「租户/公司不存在」，不落库。
- `Login`：查得用户后，校验 `user.TenantID` 对应租户存在且 `Status == 1`，否则拒绝登录（孤儿账号 → 拒登录；禁用租户 → 「该租户已被禁用，请联系管理员」）。

**3. 数据层新增事务支持（`storage/tenant.go` / `user.go` / `tool_config.go`）**

- 新增 `CreateTenantTx(ctx, tx, tenant)`：在显式事务内建租户。
- 新增 `CreateUserTx(ctx, tx, user)`：在显式事务内建用户。
- 新增 `InitDefaultToolConfigsTx(ctx, tx, tenantID)` 及其私有 `initDefaultToolConfigsWithDB`：在显式事务内初始化默认工具配置。
- 「建租户 + 建用户 + 初始化工具配置」三个子调用统一落到同一 `*gorm.DB` 事务句柄 `tx`，实现整体原子提交/回滚。

**4. 租户名唯一约束（`storage/model/models.go`）**

- `Tenant.Name` 追加 `uniqueIndex`（建立 `idx_tenants_name` 唯一索引），作为「重复注册同名租户」的 DB 层硬约束兜底；`service.RegisterTenant` 用 `isDuplicateNameErr`（匹配 MySQL 1062）把冲突转成友好提示「租户名已被注册，请更换名称」，并随事务整体回滚。

**5. JWT 载荷（`util/jwt.go`）**：保持不变（`user_id / tenant_id / role`），无需新增平台超管字段。

### 4.3 Handler 层改动（`api/handler/tenant.go` / `api/handler/user.go`）

**1. 新增 `handler.RegisterTenant`**
- 请求体：`name`（租户名）、`admin_username`、`admin_password`
- 去掉 `tenant_id`、`role` 入参（由系统决定，租户 ID 由建租户生成、角色固定 admin）
- 调 `service.RegisterTenant`，成功返回租户 + 管理员账号信息

**2. `handler.Register`（用户注册）**
- 保留 `tenant_id` / `username` / `password` / `role`（`oneof=admin member`）
- 因 `service.Register` 已补租户存在校验，handler 无需大改，但 `tenant_id` 仍需校验通过后才能注册

### 4.4 统一参数校验（`api/validator`）

沿用现有 `binding:` 标签体系，为新增 `RegisterTenant` 请求结构体加校验：
- `name`：`required,min=1,max=64`
- `admin_username`：`required,min=2,max=64`
- `admin_password`：`required,min=6,max=128`

### 4.5 审计日志

- 注册租户成功后写审计日志（operation=「注册租户」，content 记录租户名 + 管理员账号）。
- 注册用户、登录已有埋点，保持。

## 九、完成情况（实现要点 / 验证证据 / 提交记录）

### 落地实现要点
1. **公开注册租户**：新增 `POST /api/tenant/register`，成功返回 `{tenant, admin}`；调用方不可传 `tenant_id`/`role`，租户 ID 由建租户自动生成、首个账号**固定 `role=admin`**（堵问题 B / 提权）。
2. **三件套原子提交**：建租户 + 首个 admin + 默认工具配置用 `storage.DB.Transaction` 包裹，任一步失败整体回滚（堵问题 D）。私有 `POST /api/tenant` 保留管理员视角，内部与公开注册共用同一事务方法 `RegisterTenant`/`CreateTenant`。
3. **注册 / 登录校验租户存在**：`Register` 进入先 `GetTenantByID` 校验租户存在（堵问题 A）；`Login` 校验 `user.TenantID` 对应租户**存在且 `Status==1`**（堵问题 C）。
4. **租户名唯一兜底**：`tenants.name` 加唯一索引 `idx_tenants_name`，重复注册同名租户 → 明确「租户名已被注册，请更换名称」并整体回滚；同租户同名用户仍由 `users.idx_tenant_user` 拦截。
5. **参数校验**：`RegisterTenantReq` 走既有 `validator.BindJSON` + `HandleBindError`，name/admin_username/admin_password 均有 required+长度绑定校验，返回统一结构化 400。
6. **审计**：注册租户成功写审计日志（`operation='注册租户'`，content 记租户名 + 管理员账号），公开接口无当前操作者，用新建租户 ID + 管理员 ID 补齐 tenant_id/user_id，trace_id 沿用请求级。
7. **全链路 trace_id**：新 service/handler 均以 `ctx context.Context` 透传，调用 `storage.*Tx` 用 `WithContext(ctx)` 保留链路 ID；审计用 `interfaces.WithTenantUser` 补齐身份字段——符合项目 trace_id 贯穿规则。
