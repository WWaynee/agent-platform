## 一、功能现状

当前对话的存储与处理采用**单轨 Redis + 覆盖式压缩，且工具调用从不落历史**：

### 1. 存储方案（单份 Redis）

对话消息**只存一份**在 Redis，key 为 `session:{tenant_id}:{session_id}:messages`：

- `agent/memory/redis.go` 的 `RedisMemory`：Redis List 存储，每条消息单条 JSON（`{role, content}`），`RPUSH` 追加 / `LRANGE` 读取 / `DEL` 删除。
- 会话主键 ID（MySQL `sessions.id` 自增）即 Redis 里的 `session_id`。TTL 7 天，每次活跃刷新。
- 会话**元数据**（标题、时间）存 MySQL `sessions` 表；会话**对话消息本体**存 Redis。

### 2. 处理方案（覆盖式自动压缩，且只压最终问答）

`cmd/api/main.go` 装配：

```go
baseMem := memory.NewRedisMemory(storage.RDB)                                          // 底层存 Redis
agentEngine := engine.NewReActEngine(llmAdapter, tm, baseMem, "")
agentEngine.Memory = memory.NewCompressingMemory(baseMem, agentEngine)                  // 叠"超长自动压缩"装饰器
```

- `agent/memory/compressing.go` 的 `CompressingMemory` 装饰器，在每次 `AddMessage` 后检查该会话历史总 token，超过 `CompressThresholdTokens=2000` 即自动压缩。
- 压缩逻辑：拆新旧 → 旧历史经注入的 `Summarizer`（`ReActEngine.Summarize`，真实 LLM）生成中文摘要 → 组装 `[system 摘要 + 最近 3 轮原文]` → **`writeBack` 先 `base.Clear()`（Redis 即 `DEL key`）再逐条 `RPUSH` 重建**。
- 引擎读历史：`engine.Run` 从 `e.Memory.GetHistory` 拿（即读取 Redis 这份**压缩后**的历史）。
- 前端历史回看：`GetSessionMessages`（`GET /api/session/:id/messages`）用同一个 key 从 Redis 直接 `LRANGE` 读回——**读到的同样是压缩后内容**。

### 3. 工具调用当前的承载（关键现状）

```go
// agent/engine/engine.go Run 主循环（节选）
calls = append(calls, ToolCall{ToolName: parsed.Action, Params: rawInputToParams(parsed.Input)})
out, terr := e.ToolManager.ExecuteTool(*(ctx.WithRuntimeContext(toolCtx)), parsed.Action, parsed.Input)
// 工具执行结果 out（观察结果）只拼进当次请求内部的 msgs 快照：
msgs = append(msgs,
	Message{Role: "assistant", Content: raw},
	Message{Role: "user", Content: fmt.Sprintf("工具 %q 的观察结果：\n%s", parsed.Action, out)},
)

// agent/engine/engine.go persist（只存最终问答）
func (e *ReActEngine) persist(ctx AgentContext, query, answer string) {
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleUser, Content: query})
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleAssistant, Content: answer})
}
```

- **工具调用指令**（工具名 + 参数）：只打进 `AgentResponse.ToolCalls`（`[]ToolCall`）随本次 HTTP 响应返回给前端，**服务端不落库**。
- **工具执行结果**（观察结果 `out`）：只在单次请求内部 `msgs` 快照里即时消费，`persist` 不写，**下一轮/跨请求不可见**。
- **Memory 里没有工具调用**：`persist` 只写 user/assistant，所以 `RedisMemory` 与 `CompressingMemory` 的压缩对象里本来就没有工具内容。
- `memory.ChatMessage` 已定义 `RoleTool` 常量，但 `persist` 从未使用。

### 4. 数据读取出口

| 读取方 | 数据源 | 读到内容 |
|--------|--------|---------|
| 引擎 `Run`（喂 LLM） | Redis `session:{tenant}:{sid}:messages` | 压缩后历史（超长时，且不含工具过程） |
| 前端 `GetSessionMessages` | Redis 同一 key | 压缩后历史（超长时，且不含工具过程） |

## 二、存在的问题

| # | 问题 | 危害/影响 | README 关联 |
|---|------|----------|------------|
| A | 对话**只有一份存储**，压缩是"覆盖式替代"（先 DEL 再重建） | 被压缩掉的旧对话**逐字原文被永久覆盖、不可回溯**，只剩摘要大意 | 「已知设计取舍 / 待优化」 |
| B | 引擎读历史与前端回看共用**同一份**压缩后历史 | 超长后前端拿不到完整原始对话，无法做完整历史展示 / 审计回看 | 同上 |
| C | 原始历史不落盘（Redis 是内存型 + 7 天 TTL） | "永久存储"语义缺失，不是合规审计的牢靠落点 | 同上 |
| D | **工具调用指令（工具名+参数）不落库**，只随 HTTP 响应临时返回 | 丢失"这轮到底调了什么工具"的原始记录，审计/复盘只能靠运行时日志 | 本需求新增 |
| E | **工具执行结果（观察结果）不落库**，也不进长期 Memory | 下一轮 LLM 不知道上轮检索/调用获得了什么，无法复用工具结论；审计看不到推理依据 | 本需求新增 |
| F | 压缩只发生在最终问答上，**工具背景不进入压缩** | 超长后摘要里没有工具调用背景，LLM 上下文丢失"上轮调过什么、拿到什么" | 本需求新增 |

## 三、改进目标

在**热轨改动最小化 + 上下文不超窗**的前提下，实现**双轨分离存储 + 工具调用纳入完整历史与压缩**：

| 轨道 | 存储 | 用途 | 是否含工具调用 | 是否压缩 |
|------|------|------|--------------|---------|
| **冷轨（永久原文）** | **新增 MySQL `chat_messages` 表** | 完整对话（含工具指令+执行结果），供前端回看 / 审计 | ✅ 含工具指令 + 执行结果，逐条落库 | ❌ 永不压缩、永不过期、永不覆盖 |
| **热轨（喂模型）** | Redis `session:{tenant}:{sid}:messages`（改造 `persist` 写入） | 引擎 `GetHistory` 读这份 | ✅ 含"工具调用一句话摘要"，供下一轮理解+参与压缩 | ✅ 保留 `CompressingMemory` 自动压缩 |

核心底线：
1. **冷轨存逐字完整原文**：`engine.persist` 旁路写 MySQL；user 提问、assistant 回答、**工具调用指令**（工具名+参数）、**工具执行结果**（观察结果）各自落一条 `chat_messages`。携带 ctx 的 tenant/user/trace_id。
2. **热轨含工具摘要（路线 C）**：`persist` 写 Memory 时，把本轮工具调用浓缩成一句**可读中文**（`[工具] 工具名：一句话结论`），以 `user` 角色写进 Memory。这样：下一轮 LLM 记得上轮调过什么、拿到了什么；压缩时这段中文随历史一起被 `CompressingMemory` 摘要，LLM 能理解。
3. **规避 DeepSeek 协议坑**：不把工具过程写成 `role:"tool"` 消息喂 LLM（README 明确踩坑——DeepSeek 兼容 API 对 tool 角色要求前驱 assistant 带 tool_calls 会 400）。热轨一律用中文摘要以 user 角色承载。
4. **前端历史回看改读 MySQL 完整原文**：`GetSessionMessages` 不再读 Redis 那份（可能被压缩覆盖），改为读 MySQL 完整历史，含工具调用全过程。

## 四、改进方案

### 4.1 数据层改动

**1. 新增 `chat_messages` 表（`storage/model/models.go`）**

```go
// chat_message 对话消息完整历史表（永久、永不压缩；含工具调用指令与执行结果，供回看/审计）
type ChatMessage struct {
	ID        uint64 `gorm:"primaryKey"`
	TenantID  uint64 `gorm:"index:idx_chat_session;not null"`
	UserID    uint64 `gorm:"index:idx_chat_user;comment:发言/触发者用户ID"`
	SessionID uint64 `gorm:"index:idx_chat_session;not null;comment:会话ID（对应 sessions.id）"`
	Role      string `gorm:"size:16;not null;comment:user/assistant/tool"`
	Kind      string `gorm:"size:16;not null;comment:question/answer/tool_call/tool_result/system"`
	Content   string `gorm:"type:text;comment:消息内容（原始全文或工具指令/结果，永不压缩）"`
	TraceID   string `gorm:"size:128;comment:该条消息生成的全链路traceId"`
	CreatedAt time.Time
}
```

- 与引擎 `memory.ChatMessage`（`{role, content}`）字段不同（这里带 DB 主键/时间/trace/kind），**新增独立模型**避免与 `agent/memory` 包耦合。
- `Kind` 取值对齐 `memory.Role` 语义 + 扩展：`question`(用户提问)、`answer`(LLM 最终回答)、`tool_call`(工具调用指令：Content 存 `工具名 + 参数JSON`)、`tool_result`(工具执行结果：Content 存工具返回文本)、`system`(压缩摘要等，可选)。
- 索引：`(tenant_id, session_id)` 联合索引（按会话查完整历史）。
- 加入 `AllModels()`（AutoMigrate 自动建表/加列）。

**2. 新增 `storage/chat_message.go`**

- `AppendChatMessage(ctx, msg)`：`DB.WithContext(ctx)` 强制租户 + 保留 trace，写入一条原文。
- `ListChatMessagesBySession(ctx, tenantID, sessionID)`：带 `tenant_id` 强制过滤，按 `created_at`/`id` 正序返回某会话完整原文。

**3. `storage/model/models.go` 的 `AllModels()`** 追加 `&ChatMessage{}`。

### 4.2 引擎写入改动（`agent/engine/engine.go`）

**核心变化：`Run` 需收集每轮工具执行结果，`persist` 需接收工具调用序列。**

**（1）`Run` 主循环：把每轮工具调用 + 执行结果收集进结构体**

```go
type toolRecord struct {
	call   ToolCall // 工具调用指令（工具名 + 参数）
	result string   // 工具执行结果（观察结果 out）
}

// Run 内：
var toolRecords []toolRecord
for iter := 0; iter < e.MaxIterations; iter++ {
	// ... 解析出 parsed.Action
	if parsed.Action == finalAnswerAction {
		e.persist(ctx, query, parsed.Input, toolRecords)
		return &AgentResponse{Answer: parsed.Input, ToolCalls: calls}, nil
	}
	calls = append(calls, ToolCall{ToolName: parsed.Action, Params: rawInputToParams(parsed.Input)})
	out, terr := e.ToolManager.ExecuteTool(*(ctx.WithRuntimeContext(toolCtx)), parsed.Action, parsed.Input)
	if terr != nil {
		out = fmt.Sprintf("工具 %q 执行失败: %v", parsed.Action, terr)
	}
	// 收集工具调用记录（供冷轨落库 + 热轨摘要）
	toolRecords = append(toolRecords, toolRecord{
		call:   ToolCall{ToolName: parsed.Action, Params: rawInputToParams(parsed.Input)},
		result: out,
	})
	// ... 仍拼进当次 msgs 继续循环
}
```

**（2）`persist` 签名扩展 + 双轨写入**

```go
func (e *ReActEngine) persist(ctx AgentContext, query, answer string, toolRecords []toolRecord) {
	// ① 热轨（Redis，超长自动压缩）——含工具一句话摘要（路线 C）
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleUser, Content: query})
	for i, tr := range toolRecords {
		e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{
			Role:    memory.RoleUser, // 规避 tool 角色喂 LLM 的 DeepSeek 协议坑，用 user 承载
			Content: summarizeToolCall(tr), // 工具调用一句话中文摘要：如 "[工具] knowledge_retrieve：查到了职工带薪年假规定，未来回答可引用"
		})
		_ = i
	}
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleAssistant, Content: answer})

	// ② 冷轨（MySQL，永不压缩）——完整原文逐条落库（尽力而为，失败只 warn）
	e.persistFullHistory(ctx, query, answer, toolRecords)
}
```

- `summarizeToolCall`：把工具调用收敛成一句可读中文。规则——`[工具] <工具名>：<从执行结果提炼的一句话要点>`。要点提炼可用固定模板（如取结果首行/前 N 字符）或调用 Summarizer 摘要。**本项目不 eval 工具结果原文默认只落冷轨**，热轨摘要取结果前 N 个字（避免把巨量检索片段塞进上下文）。建议 `ToolSummaryMaxChars` 常量（如 80 字）。
- 若某轮工具执行失败，`summarizeToolCall` 输出"`[工具] 工具名：调用失败 (<错误信息>)`"，让下一轮 LLM 知道上轮工具坏了。

**（3）`persistFullHistory`（冷轨全量落库）**

```go
func (e *ReActEngine) persistFullHistory(ctx AgentContext, query, answer string, toolRecords []toolRecord) {
	base := ctx.ToContext(nil) // 带 tenant/user/trace_id 的标准 ctx
	sink := e.fullHistorySink() // 注入的 FullHistorySink（见 4.3），nil 则跳过
	if sink == nil {
		return
	}
	// 逐条写：提问、每个工具指令+结果、最终回答，按时间正序
	if err := sink.Append(base, ChatMsg{TenantID: ctx.TenantID, UserID: ctx.UserID, SessionID: ctx.SessionID, Role: "user", Kind: "question", Content: query}); err != nil {
		observability.WithAgentContext(ctx).Warn("写完整历史失败(提问)", zap.Error(err))
	}
	for _, tr := range toolRecords {
		// 工具调用指令
		if err := sink.Append(base, ChatMsg{TenantID: ctx.TenantID, UserID: ctx.UserID, SessionID: ctx.SessionID, Role: "tool", Kind: "tool_call", Content: fmt.Sprintf("%s %s", tr.call.ToolName, mustJSON(tr.call.Params))}); err != nil {
			observability.WithAgentContext(ctx).Warn("写完整历史失败(工具指令)", zap.Error(err))
		}
		// 工具执行结果
		if err := sink.Append(base, ChatMsg{TenantID: ctx.TenantID, UserID: ctx.UserID, SessionID: ctx.SessionID, Role: "tool", Kind: "tool_result", Content: tr.result}); err != nil {
			observability.WithAgentContext(ctx).Warn("写完整历史失败(工具结果)", zap.Error(err))
		}
	}
	if err := sink.Append(base, ChatMsg{TenantID: ctx.TenantID, UserID: ctx.UserID, SessionID: ctx.SessionID, Role: "assistant", Kind: "answer", Content: answer}); err != nil {
		observability.WithAgentContext(ctx).Warn("写完整历史失败(回答)", zap.Error(err))
	}
}
```

> 设计：冷轨"尽力而为"，任一写失败只 warn、不阻塞对话（对齐 `RecordAuditLog` 风格）；逐条写保证顺序就是对话真实时序。`Kind` 区分记录了工具**指令**和**结果**两个独立事实，便于审计区分"打算调/调了什么"与"返回了什么"。

**（4）热轨与冷轨内容不同（关键）**：
- 热轨（喂 LLM）只放 `user 提问 + 工具一句话摘要 + assistant 回答`——轻量、不超窗、LLM 能理解；
- 冷轨（MySQL 完整）放 `提问 + 工具名参数 + 工具结果全文 + 回答`——完整、逐字、可审计。

### 4.3 装配（`cmd/api/main.go`）

- `engine` 不能 import `storage`（否则成环）。在 `engine` 定义最小注入接口：

```go
// engine/sink.go
type FullHistorySink interface {
	Append(ctx context.Context, m ChatMsg) error
}
type ChatMsg struct {
	TenantID, UserID, SessionID uint64
	Role, Kind, Content, TraceID string
}
```

- `ReActEngine` 增加字段 `fullHistorySink FullHistorySink` 与 setter `SetFullHistorySink(s)`（nil 安全）。
- `cmd/api/main.go` 用 adapter 把 `storage.AppendChatMessage` 接进来：

```go
type chatMsgSink struct{ d *gorm.DB }
func (s chatMsgSink) Append(ctx context.Context, m engine.ChatMsg) error {
	return storage.AppendChatMessage(ctx, storage.ChatMessage{
		TenantID: m.TenantID, UserID: m.UserID, SessionID: m.SessionID,
		Role: m.Role, Kind: m.Kind, Content: m.Content, TraceID: interfaces.TraceIDFromCtx(ctx),
	})
}
agentEngine.SetFullHistorySink(chatMsgSink{d: storage.DB})
```

### 4.4 读取改动（`api/service/session.go` / `api/handler/session.go`）

- `GetSessionMessages(ctx, tenantID, userID, id)` 取数源改读 MySQL 完整原文（`storage.ListChatMessagesBySession`），不再 `LRANGE` 读 Redis。
- 越权防线不变：仍先 `storage.GetSessionByID(ctx, tenantID, id)` 带租户过滤 + `s.UserID != userID` 本人校验，再取数。
- **返回契约扩展**：原 `[{role, content}]` 需带上 `kind`，以便前端区分工具指令/结果如何展示。建议返回 `[{role, kind, content}]`（`kind` 新增字段，前端按其渲染问答 vs 工具调用）。

> 注：`DeleteSession` 删除会话时 MySQL `chat_messages` 是否级联删除——**默认保留**（永久审计落点），范围外不做级联。

### 4.5 日志 / trace 规范

- 所有新增写入走 `storage.AppendChatMessage(ctx, ...)`，内部 `DB.WithContext(ctx)`（GORM logger 自动带 trace_id/tenant_id）；`TraceID` 字段从 `interfaces.TraceIDFromCtx(ctx)` 取（经 `AgentContext.ToContext(nil)` 译成标准 ctx，贯穿到冷轨落库）。
- 错误日志统一走 `observability.WithAgentContext`/`WithContext`，字段用 `observability.Field*` 常量，禁止 `fmt.Printf`。

### 4.6 审计

- 本期不新增审计埋点（读取会话历史非写操作）。如需"查看历史"审计，后续可扩（范围外）。

## 八、上线前注意

- 本需求单涉及**新增表**：启动前需跑 `go run cmd/migrate/main.go` 让 `chat_messages` 表通过 AutoMigrate 建出；或手动执行等价 DDL。
- **热轨语义变化**：`persist` 不再只存最终问答，会多写工具摘要 user 消息——`CompressingMemory` 触发更频繁，需验证压缩阈值下对话仍正常、不超窗。
- **DeepSeek 协议兼容**：热轨工具摘要一律用 `user` 角色（不用 tool 角色），规避 README 记录的 `role:"tool"` 触发 HTTP 400 的坑；上线前在回归里显式验证一轮含工具对话。
- **`GetSessionMessages` 返回契约变更**：新增 `kind` 字段，前端如需继续按 `[{role,content}]` 展示需向后适配；若前端暂不改，可先用 `role` 兜底（tool_call→tool 角色渲染），本期建议同步暴露 `kind` 便于前端后续增强。
- `docker-compose`、中间件、`.env` 无需新增配置。
