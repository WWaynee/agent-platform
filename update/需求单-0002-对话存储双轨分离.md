## 一、功能现状

当前（需求单 0001 交付后）对话的存储与处理采用**单轨 Redis + 覆盖式压缩**：

### 1. 存储方案（单份 Redis）

对话消息**只存一份**在 Redis，key 为 `session:{tenant_id}:{session_id}:messages`：

- `agent/memory/redis.go` 的 `RedisMemory`：Redis List 存储，每条消息单条 JSON（`{role, content}`），`RPUSH` 追加 / `LRANGE` 读取 / `DEL` 删除。
- 会话主键 ID（MySQL `sessions.id` 自增）即 Redis 里的 `session_id`。TTL 7 天，每次活跃刷新。
- 会话**元数据**（标题、时间）存 MySQL `sessions` 表；会话**对话消息本体**存 Redis。

### 2. 处理方案（覆盖式自动压缩）

`cmd/api/main.go` 装配：

```go
baseMem := memory.NewRedisMemory(storage.RDB)                                          // 底层存 Redis
agentEngine := engine.NewReActEngine(llmAdapter, tm, baseMem, "")
agentEngine.Memory = memory.NewCompressingMemory(baseMem, agentEngine)                  // 叠"超长自动压缩"装饰器
```

- `agent/memory/compressing.go` 的 `CompressingMemory` 装饰器，在每次 `AddMessage` 后检查该会话历史总 token，超过 `CompressThresholdTokens=2000` 即自动压缩。
- 压缩逻辑：拆新旧 → 旧历史经注入的 `Summarizer`（`ReActEngine.Summarize`，真实 LLM）生成中文摘要 → 组装 `[system 摘要 + 最近 3 轮原文]` → **`writeBack` 先 `base.Clear()`（Redis 即 `DEL key`）再逐条 `RPUSH` 重建**。
- 引擎读历史：`engine.Run` 从 `e.Memory.GetHistory` 拿（即读取 Redis 这份**压缩后**的历史）。
- 前端历史回看：`GetSessionMessages`（`GET /api/session/:id/messages`）用同一个 key 从 Redis 直接 `LRANGE` 读回——**读到的同样是压缩后内容**。

### 3. 数据读取出口

| 读取方 | 数据源 | 读到内容 |
|--------|--------|---------|
| 引擎 `Run`（喂 LLM） | Redis `session:{tenant}:{sid}:messages` | 压缩后历史（超长时） |
| 前端 `GetSessionMessages` | Redis 同一 key | 压缩后历史（超长时） |

## 二、存在的问题

| # | 问题 | 危害/影响 | README 关联 |
|---|------|----------|------------|
| A | 对话**只有一份存储**，压缩是"覆盖式替代"（先 DEL 再重建） | 被压缩掉的旧对话**逐字原文被永久覆盖、不可回溯**，只剩摘要大意 | 「已知设计取舍 / 待优化」 |
| B | 引擎读历史与前端回看共用**同一份**压缩后历史 | 超长后前端拿不到完整原始对话，无法做完整历史展示 / 审计回看 | 同上 |
| C | 原始历史不落盘（Redis 是内存型 + 7 天 TTL） | "永久存储"语义缺失，不是合规审计的牢靠落点 | 同上 |

## 三、改进目标

在**不改动 ReAct 引擎热路径 / 压缩逻辑**（引擎仍读 Redis 压缩版、上下文不超窗）的前提下，实现**双轨分离存储**，让"原始完整历史可永久回溯"：

| 轨道 | 存储 | 用途 | 是否有压缩 |
|------|------|------|-----------|
| **热轨（喂模型）** | Redis `session:{tenant}:{sid}:messages`（现状不动） | 引擎 `GetHistory` 读这份 | ✅ 保留 `CompressingMemory` 自动压缩 |
| **冷轨（永久原文）** | **新增 MySQL `chat_messages` 表** | 完整原始对话，供前端回看 / 审计 | ❌ 永不压缩、永不过期、永不覆盖 |

核心底线：
1. **引擎热路径零改动**：`RedisMemory` + `CompressingMemory` 原样保留，引擎 `GetHistory` 依旧读 Redis 压缩版。
2. **完整原文永久落 MySQL**：`engine.persist` 旁路写一条 `chat_messages`（user/assistant 各一条），携带 ctx 的 tenant/user/trace_id。
3. **前端历史回看改读 MySQL 完整原文**：`GetSessionMessages` 不再读 Redis 那份（可能被压缩覆盖），改为读 MySQL 完整历史，回看 / 审计拿到的是逐字原文。

## 四、改进方案

### 4.1 数据层改动

**1. 新增 `chat_messages` 表（`storage/model/models.go`）**

```go
// chat_message 对话消息完整历史表（永久、永不压缩；引擎热路径仍走 Redis，本表供完整回看/审计）
type ChatMessage struct {
	ID        uint64 `gorm:"primaryKey"`
	TenantID  uint64 `gorm:"index:idx_chat_session;not null"`
	UserID    uint64 `gorm:"index:idx_chat_user;comment:发言者用户ID"`
	SessionID uint64 `gorm:"index:idx_chat_session;not null;comment:会话ID（对应 sessions.id）"`
	Role      string `gorm:"size:16;not null;comment:user/assistant"`
	Content   string `gorm:"type:text;comment:消息内容（原始全文，永不压缩）"`
	TraceID   string `gorm:"size:128;comment:该条消息生成的全链路traceId"`
	CreatedAt time.Time
}
```

- 加入 `AllModels()`（AutoMigrate 自动建表/加列）。
- 索引：`(tenant_id, session_id)` 联合索引（按会话查历史）、`(tenant_id, user_id)`（按用户维度查）。
- 与引擎 `RedisMemory` 的 `ChatMessage` 字段不同（这里带 DB 主键/时间/trace），**新增独立模型**避免与 `agent/memory` 包耦合。

**2. 新增 `storage/chat_message.go`**

- `AppendChatMessage(ctx, msg)`：`DB.WithContext(ctx)` 强制租户 + 保留 trace，写入一条原文。
- `ListChatMessagesBySession(ctx, tenantID, sessionID)`：带 `tenant_id` 强制过滤，按 `created_at`/`id` 正序返回某会话完整原文。

**3. `storage/model/models.go` 的 `AllModels()`** 追加 `&ChatMessage{}`。

### 4.2 写入改动（`agent/engine/engine.go` 的 `persist`）

在 `persist` 写 Redis 后，**旁路写一条到 MySQL**（尽力而为，失败不中断对话，对齐 `RecordAuditLog` 风格）：

```go
func (e *ReActEngine) persist(ctx AgentContext, query, answer string) {
	// ① 引擎即时历史（Redis，超长自动压缩）——现状不动
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleUser, Content: query})
	e.Memory.AddMessage(ctx.TenantID, ctx.SessionID, memory.ChatMessage{Role: memory.RoleAssistant, Content: answer})

	// ② 永久完整原文（MySQL，永不压缩）——旁路写入，失败只 warn 不影响对话
	e.persistFullHistory(ctx, query, answer)
}
```

> 说明：`ChatMessage` 模型与 `storage` 已存在约定（GORM 模型在 `storage/model`，存储方法在 `storage/*.go`），且 `engine` 已持有 `AgentContext`（含 `TenantID`/`UserID`/`SessionID`/`TraceID`）。为保持 `engine` 不反向依赖 `api/service`，把"写永久原文"的存储方法落在 `storage` 层，由 `engine` 通过一个**可注入的回调/接口**调用（见 4.3 装配），避免循环依赖。

### 4.3 装配（`cmd/api/main.go`）

- 新增 `storage.InitChatMessageStore()` 或直接复用 `storage.DB`；在 `cmd/api/main.go` 把"写 MySQL 原文"的持久化器注入 engine（或直接调用 `storage.AppendChatMessage`）。
- 因 `engine` 不能 import `storage`（否则成环），建议在 `engine` 定义最小接口 `FullHistorySink{ Append(ctx, msg) error }`，`main` 里用一个 adapter 把 `storage.AppendChatMessage` 接进来。

### 4.4 读取改动（`api/service/session.go` / `api/handler/session.go`）

- `GetSessionMessages(ctx, tenantID, userID, id)` 的**取数源改读 MySQL 完整原文**（`storage.ListChatMessagesBySession`），不再 `LRANGE` 读 Redis 那份（可能被压缩覆盖）。
- 越权防线不变：仍先 `storage.GetSessionByID(ctx, tenantID, id)` 带租户过滤 + `s.UserID != userID` 本人校验，再取数。
- handler 不变（仍返回 `[{role, content}]` 正序），前端无感知。

> 注：`DeleteSession` 删除会话时，MySQL `chat_messages` 是否级联删除——**默认保留**（本表是"永久审计落点"），如需随会话清理可后续加 `deleted_at`/条件删除，本期不做级联。

### 4.5 日志 / trace 规范

- 所有新增写入走 `storage.AppendChatMessage(ctx, ...)`，内部 `DB.WithContext(ctx)`，GORM logger 自动带 trace_id/tenant_id；写入的 `TraceID` 字段从 `interfaces.TraceIDFromCtx(ctx)` 取（经 `AgentContext.ToContext(nil)` 译成标准 ctx）。
- 错误日志统一走 `observability`（`WithAgentContext` / `WithContext`），字段用 `observability.Field*` 常量，禁止 `fmt.Printf`。

### 4.6 审计

- 本期不新增审计埋点（读取会话历史非写操作）。如需"查看历史"审计，后续可扩（范围外）。
